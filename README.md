# Лабораторна робота №7 — варіант 5

Servlet та REST API для авіакомпанії. Java 21, вбудований Jetty 12, Jakarta Servlet 6.0, Jackson, Jakarta Validation та JUnit 5. Spring, JAX-RS та інші вебфреймворки не використовуються.

## Запуск

Команди виконуються з кореня проєкту:

```sh
./gradlew clean build
./gradlew run
```

Порт і всі шляхи задані у `src/main/resources/app.properties`. За стандартної конфігурації сервер доступний на `http://localhost:8080`. Значення `server.port=0` дозволяє ОС вибрати вільний порт; Main виводить фактичну адресу. Відсутній або порожній ключ конфігурації спричиняє виняток із назвою ключа, некоректний порт теж відхиляється.

Main завантажує `data/passengers.json` і `data/flights.yaml` через DataLoader та показує кількість прочитаних, доданих і відкинутих записів. У кожному файлі 15 записів: 11 додаються, 4 відкидаються. Файли містять навмисні помилки й залишаються без змін.

Для завершення натисніть **Ctrl+C** у терміналі, де працює сервер. Shutdown hook спочатку зупиняє Jetty, а потім зберігає пасажирів у `state/passengers.json`, рейси — у `state/flights.yaml`. Папка створюється автоматично; її вміст не відстежується Git. Шляхи збереження перевіряються, щоб не перезаписати вхідні файли або один одного. Щоб наступного разу завантажити збережений стан, змініть відповідні вхідні шляхи у `app.properties`.

## Маршрути

| Метод | Шлях | Параметри / тіло | Успіх | Помилки |
|---|---|---|---|---|
| GET | `/api/passengers` | `name`, `birthFrom`, `birthTo`, `sort`, `order`, `limit`, `offset` | 200, масив | 400 |
| GET | `/api/passengers/{id}` | `{id}` — серія й номер паспорта | 200, об’єкт | 404 |
| POST | `/api/passengers` | JSON пасажира | 201, об’єкт і Location | 400, 409, 415 |
| PUT | `/api/passengers/{id}` | JSON пасажира з тією самою identity | 200, об’єкт | 400, 404, 415 |
| DELETE | `/api/passengers/{id}` | — | 204, без тіла | 404 |
| GET | `/api/passengers/stats` | — | 200, об’єкт `byBirthYear` | 400 для параметрів |
| GET | `/api/flights` | `number`, `departureFrom`, `departureTo`, `sort`, `order`, `limit`, `offset` | 200, масив | 400 |
| GET | `/api/flights/{id}` | `{id}` — номер рейсу | 200, об’єкт | 404 |
| POST | `/api/flights` | JSON рейсу | 201, об’єкт і Location | 400, 409, 415 |
| PUT | `/api/flights/{id}` | JSON рейсу з тією самою identity | 200, об’єкт | 400, 404, 415 |
| DELETE | `/api/flights/{id}` | — | 204, без тіла | 404 |
| GET | `/api/flights/stats` | — | 200, `byStatus` і `totalDurationMinutes` | 400 для параметрів |

Невідомий шлях і зайвий сегмент дають 404. Метод, який не підтримується на вибраному шляху, дає 405, зокрема POST до окремого об’єкта або DELETE до колекції. Усі ці помилки мають JSON-формат ApiError. Значення identity `stats` зарезервоване для статистики й відхиляється при POST.

Пасажир має поля `passportSeriesNum`, `fullName`, `birthDate`; рейс — `flightNumber`, `departureAirport`, `arrivalAirport`, `departureTime`, `arrivalTime`, `status`. Приклади тіл є у `requests.http`.

## Фільтри, сортування й пагінація

- `name` — частковий збіг імені пасажира без урахування регістру; `number` — такий самий пошук за номером рейсу.
- `birthFrom`, `birthTo` задають включний діапазон дат народження `yyyy-MM-dd`.
- `departureFrom`, `departureTo` задають включний діапазон часу вильоту, наприклад `2026-12-01T10:00:00`.
- Можна вказати тільки одну межу діапазону. Початок, пізніший за кінець, дає 400.
- Для пасажирів `sort` приймає `passportSeriesNum` (типово), `fullName` або `birthDate`; для рейсів — `flightNumber` (типово), `departureTime` або `status`. При однаковому значенні поля порядок визначається identity.
- `order` — `ASC` (типово) або `DESC`; перетворюється на SortOrder. Відповідність sort компаратору зберігається у Map; сортування виконує `findAllSorted`.
- `offset` типово дорівнює 0, відсутній `limit` означає всі результати. Обидва параметри — цілі числа від 0 до 2147483647. `limit=0` або offset за межами результату повертає порожній масив.

Фільтри викликають доменні методи пошуку репозиторіїв; після перетину умов застосовуються сортування та пагінація. Усі параметри можна комбінувати. Наприклад:

```http
GET /api/passengers?name=Анна&birthFrom=1990-01-01&sort=birthDate&order=DESC&limit=5&offset=0
```

## JSON та помилки

FileStorage і JsonSupport використовують спільні налаштування JsonMappers. ObjectMapper створюється один раз і після налаштування не змінюється. Дати й час передаються ISO-рядками. Кожна відповідь із тілом має `Content-Type: application/json; charset=UTF-8`; DELETE 204 не має тіла.

POST і PUT вимагають `application/json`; параметр `charset=UTF-8` допускається. Некоректний JSON, неправильний тип кореня або поля, помилка конструктора й порушення Jakarta Validation дають 400. Для валідації повертаються всі порушення, включно з `@ValidFlightTimes`, і дані в репозиторії не змінюються.

Невідомі JSON-поля відхиляються з 400. Службове `createdAt` рейсу явно ігнорується анотацією моделі й не передається клієнту. Невідомі, повторені та порожні параметри GET теж відхиляються з 400. Параметри підтримуються тільки для GET колекції; для інших шляхів і методів вони відхиляються.

ErrorHandlingFilter — єдине місце перетворення винятків на HTTP-відповідь. Формат ApiError:

```json
{
  "status": 400,
  "error": "Bad Request",
  "message": "Тіло запиту не пройшло валідацію",
  "path": "/api/flights",
  "violations": [
    {"field": "arrivalTime", "message": "Час прибуття має бути пізнішим за час вильоту"}
  ]
}
```

Для інших помилок `violations` — порожній масив. DuplicateIdentityException дає 409. Неочікувана помилка дає 500 із загальним повідомленням; текст винятку і stack trace не потрапляють у відповідь.

Location містить закодовану identity як один сегмент URL. Шлях ділиться на сегменти до декодування, тому пробіли, кирилиця, знак `+`, `%` та закодований `/` усередині identity пасажира зберігаються. Назовні завжди передається Location, який можна використати для GET, PUT або DELETE без повторного кодування.

## Паралельність і логування

Доступ до приватної LinkedHashMap репозиторію захищений synchronized: перевірка й додавання, заміна та видалення виконуються під одним монітором. Окрема перевірка наявності ключа перед записом не підходить: два потоки можуть одночасно побачити, що ключа немає, і обидва оголосити створення успішним. Читання повертає знімок списку, а stream працює над цим знімком, тому паралельна зміна Map не спричиняє ConcurrentModificationException.

Сервлети зберігають лише репозиторій, JsonSupport і таблицю компараторів; дані конкретного запиту залишаються локальними змінними. Репозиторії отримуються через конструктори, статичних сховищ немає.

RequestLoggingFilter стоїть зовні ErrorHandlingFilter, тому бачить остаточний статус, зокрема 500. Для кожного запиту він пише один рядок: метод, шлях із параметрами, статус і тривалість у мілісекундах. Рівні: 2xx — INFO, 4xx — WARN, 5xx — ERROR. Stack trace неочікуваного винятку один раз записує тільки ErrorHandlingFilter. Логи англомовні й зберігаються у `logs/application.log`.

## Перевірка

```sh
./gradlew test
```

ApiServerTest і ApiLoggingTest щоразу запускають справжній сервер на порту 0 зі свіжими репозиторіями й надсилають запити через java.net.http.HttpClient. Дані тестів створюються в пам’яті й не залежать від файлів у data. Перевіряються CRUD обох сутностей, статуси помилок, усі порушення валідації, кирилиця, спеціальні символи, комбінування параметрів, статистика, паралельні операції, остаточний статус у логах і приховування діагностики 500. Попередні тести моделей, файлів та репозиторіїв теж виконуються.

`requests.http` містить запити для ручної перевірки у VS Code REST Client або IntelliJ HTTP Client. Запускайте їх зверху вниз: створення перед дублікатом, оновленням і видаленням. Повний повтор сценарію можливий після перезапуску сервера, який типово знову завантажує початкові data-файли. Якщо змінили порт, оновіть `@baseUrl` на початку файлу.

Довідка: [вбудовані сервлети Jetty](https://jetty.org/docs/jetty/12/programming-guide/server/http.html#pg-server-http-handler-use-servlet).
