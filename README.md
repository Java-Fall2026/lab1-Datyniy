### 📋 Що зробити

#### Частина 1. Сервер і маршрути

**1. Сервер.** Клас `ApiServer` (назви репозиторіїв — з вашого домену):

```java
public class ApiServer {
    public ApiServer(int port, RoomRepository rooms, GuestRepository guests) { ... }

    public void start() throws Exception
    public void stop() throws Exception
    public int port()
}
```

Порт береться з `app.properties` (ключ `server.port`), правило про відсутній ключ — те саме, що в ЛР6. Порт `0` означає «будь-який вільний»; `port()` повертає той, який сервер справді отримав. Тести працюють саме так.

`ApiServer` один раз створює `JsonSupport` (пункт 5), обидва сервлети й обидва фільтри (пункти 7 і 9) і реєструє їх у Jetty.

**2. Доменні сервлети.** Для кожної з двох сутностей — свій сервлет, що напряму успадковує `HttpServlet`:

```java
public class RoomServlet extends HttpServlet {
    public RoomServlet(RoomRepository repository, JsonSupport json) { ... }
    ...
}
```

Репозиторій і `JsonSupport` потрапляють у сервлет через конструктор. Статичних полів-синглтонів на кшталт `Repositories.ROOMS` немає.

Спільного предка в сервлетів немає. Спільний код вони не успадковують, а використовують: читання й запис JSON — через `JsonSupport`, перетворення виключень на відповіді — через фільтр. Сервлет розбирає шлях і параметри, звертається до репозиторію й пише відповідь — і все. Якщо розбір шляху однаковий в обох сервлетах, винесіть його в окремий допоміжний клас.

У `GenericRepository<T>` додайте два методи:

```java
public boolean replace(T item)
public String identityOf(T item)
```

`replace` замінює об'єкт із тією самою identity. Якщо такого об'єкта немає, нічого не додає й повертає `false`. `identityOf` повертає identity об'єкта: сервлет потребує її для `Location` і для перевірки `PUT`. Сам `IdentityExtractor` лишається приватним полем.

**3. Маршрути.** Кожен доменний сервлет змаплений на `/api/<сутність>/*` і обслуговує:

| Метод | Шлях | Успіх | Помилки |
|---|---|---|---|
| `GET` | `/api/rooms` | 200, масив | 400 — невалідний параметр |
| `GET` | `/api/rooms/{id}` | 200, об'єкт | 404 |
| `POST` | `/api/rooms` | 201, об'єкт і заголовок `Location` | 400, 409, 415 |
| `PUT` | `/api/rooms/{id}` | 200, об'єкт | 400, 404, 415 |
| `DELETE` | `/api/rooms/{id}` | 204, без тіла | 404 |

- `Location` у відповіді на `POST` — шлях до створеного об'єкта: `/api/rooms/101`.
- `PUT`, у якого identity в тілі не збігається з `{id}` у шляху, — 400: змінити identity через `PUT` не можна.
- Метод, якого для цього шляху немає (`DELETE /api/rooms`, `POST /api/rooms/101`), — 405. Шлях на кшталт `/api/rooms/101/extra` — 404.
- Якщо identity у вашому домені може містити пробіли, кирилицю чи інші спецсимволи, запит до такого об'єкта має працювати.

**4. Параметри запиту.** `GET` колекції приймає:

- `sort` і `order` — сортування через `findAllSorted` із ЛР5, `order` перетворюється на `SortOrder`. Відповідність назви в `sort` компаратору — через `Map<String, Comparator<T>>`, а не ланцюжок `if` чи `switch` по рядках;
- щонайменше два параметри фільтрації, що викликають ваші методи пошуку з ЛР5: текстовий і за діапазоном;
- `limit` і `offset` — пагінація.

Параметри комбінуються в одному запиті: `?minPrice=500&sort=price&order=DESC&limit=5`.

Невідоме значення `sort`, `order=SIDEWAYS`, `limit=-5`, `limit=abc` — 400 з поясненням, що не так. Не 500 і не мовчазне ігнорування.

Окремий шлях для агрегації (наприклад, `/api/rooms/stats`) повертає JSON-об'єкт із результатом одного з методів групування чи агрегації з ЛР5.

#### Частина 2. JSON, валідація, помилки

**5. JSON — `JsonSupport`.** Тіло запиту й відповіді обробляє один допоміжний клас, спільний для обох сервлетів:

```java
public class JsonSupport {
    public JsonSupport(ObjectMapper mapper, Validator validator) { ... }

    public <T> T readValid(HttpServletRequest request, Class<T> type) throws IOException
    public <T> void write(HttpServletResponse response, int status, T body) throws IOException
}
```

`readValid` перевіряє `Content-Type`, розбирає тіло й проганяє результат через валідатор. Якщо щось не так, метод кидає виключення, а фільтр із пункту 7 перетворює його на 415 або 400. `write` виставляє статус і `Content-Type` та записує тіло.

Під капотом — Jackson із ЛР6. Налаштування `ObjectMapper` (дати рядками ISO тощо) зберіть в одному місці, спільному для `FileStorage` і `JsonSupport`, щоб файли й API не роз'їхалися у форматі. `ObjectMapper` створюється один раз, а не на кожен запит.

- Кожна відповідь із тілом має `Content-Type: application/json; charset=UTF-8`. Перевірте на об'єкті з кирилицею.
- `POST` і `PUT` з `Content-Type`, відмінним від `application/json`, — 415.
- Синтаксично битий JSON і JSON не того типу (масив замість об'єкта, рядок у числовому полі) — 400.
- Як поводитися з невідомим полем у тілі й невідомим параметром запиту — відкидати з 400 чи ігнорувати — ваше рішення. Опишіть його в `README.md`.

**6. Валідація.** Тіло `POST` і `PUT` у `readValid` проходить через той самий `Validator`, що й `DataLoader` у ЛР6, разом із вашою власною анотацією. Невалідне тіло — 400, і у відповіді всі порушення, а не лише перше. Об'єкт, що не пройшов валідацію, у репозиторій не потрапляє.

Якщо частину перевірок ви лишили в конструкторі (ЛР6), виключення з конструктора під час розбору тіла — теж 400, а не 500.

**7. Обробка помилок — `ErrorHandlingFilter`.** Окремий `jakarta.servlet.Filter` на `/*` обгортає всі сервлети. Він викликає `chain.doFilter(...)`, перехоплює виключення, що вилетіли із сервлета, і перетворює їх на статус і тіло `ApiError`. Це єдине місце в програмі, де виключення стає HTTP-відповіддю: у сервлетах і в `JsonSupport` немає `try/catch` заради статусу.

Для ситуацій, яким не відповідає жодне наявне виключення (об'єкт не знайдено, невалідний параметр, не той `Content-Type`), заведіть власні unchecked-виключення. Як їх організувати й як фільтр дізнається з виключення статус — ваше рішення.

Будь-яка помилка — 400, 404, 405, 409, 415, 500 — повертається тілом одного формату, record `ApiError`:

```json
{
  "status": 400,
  "error": "Bad Request",
  "message": "Тіло запиту не пройшло валідацію",
  "path": "/api/rooms",
  "violations": [
    { "field": "capacity", "message": "Місткість має бути додатною" },
    { "field": "number",   "message": "Номер кімнати не може бути порожнім" }
  ]
}
```

`violations` заповнюється тільки для помилок валідації; в інших помилках це порожній список.

- `DuplicateIdentityException` — 409.
- Непередбачене виключення — 500. У тілі — загальне повідомлення, без stack trace і без тексту виключення; stack trace `ErrorHandlingFilter` пише в лог.
- 404 на шлях, якого немає взагалі (`/api/unknown`), і 405 — теж у форматі `ApiError`, а не HTML-сторінкою Jetty чи `HttpServlet`.

#### Частина 3. Паралельність, логування, тести

**8. Паралельні запити.** Jetty обслуговує запити пулом потоків, а екземпляр сервлета — один на всі. Отже:

- сервлет не зберігає дані конкретного запиту в своїх полях;
- репозиторій витримує паралельні `add`, `replace` і `removeByIdentity`. Два одночасні `POST` з однією identity дають рівно один 201 і один 409, а не два 201 і не 500.

Як ви цього досягли — ваше рішення. Поля `GenericRepository` лишаються приватними. Поясніть рішення в `README.md` двома-трьома реченнями, зокрема чому перевірка «чи є такий ключ» і запис окремими кроками тут не годяться.

**9. Фільтр логування через SLF4J.** Другий `jakarta.servlet.Filter` на `/*` логує кожен запит одним рядком: метод, шлях із параметрами, статус відповіді, тривалість у мілісекундах. Рівень — за статусом: 2xx — `INFO`, 4xx — `WARN`, 5xx — `ERROR`.

Фільтр логування бачить остаточний статус, зокрема 500, який виставив `ErrorHandlingFilter`. Stack trace непередбаченого виключення логується один раз — в `ErrorHandlingFilter`. Фільтр логування пише лише рядок запиту.

**10. Оновіть `Main`.** Він має:

1. прочитати з `app.properties` порт і шляхи до файлів;
2. завантажити обидва файли через `DataLoader` з ЛР6 і вивести підсумок: скільки прочитано, додано, відкинуто;
3. запустити сервер і вивести адресу, за якою його шукати;
4. при зупинці (Ctrl+C) через shutdown hook зупинити сервер і зберегти вміст обох репозиторіїв через `FileStorage`. Шляхи для збереження — теж у `app.properties`, і це не ті файли, що лежать у `data/`: ваші файли з навмисними помилками не перезаписуються.

**11. Сценарії запитів.** Файл `requests.http` у корені репозиторію (HTTP Client в IntelliJ IDEA або REST Client у VS Code): щонайменше по запиту на кожен рядок таблиці з пункту 3 і на кожен статус помилки — 400 (валідація, битий JSON, невалідний параметр), 404, 405, 409, 415. На захисті ви запускаєте сервер і проганяєте ці запити.

**12. Тести на JUnit 5, щонайменше дванадцять.** Тести піднімають справжній сервер на порту `0`, щоразу зі свіжими репозиторіями, і ходять до нього через `java.net.http.HttpClient`. Тести не залежать від порядку запуску й від файлів у `data/`.

- `GET` колекції: 200, масив очікуваної довжини, `Content-Type` містить `application/json` і `charset=UTF-8`;
- `GET` за identity: 200 для наявного об'єкта, 404 з тілом `ApiError` для відсутнього;
- `POST` валідного об'єкта: 201, `Location`, і `GET` за цим `Location` повертає той самий об'єкт;
- `POST` невалідного об'єкта: 400, у `violations` очікувана кількість порушень, серед них — порушення власної анотації; розмір репозиторію не змінився;
- `POST` дубліката: 409, розмір репозиторію не змінився;
- `POST` синтаксично битого JSON — 400, а не 500;
- `POST` з `Content-Type: text/plain` — 415;
- `PUT`: наявний об'єкт — 200 і зміна видна в `GET`; відсутній — 404; identity в тілі не збігається зі шляхом — 400;
- `DELETE`: 204, після нього `GET` — 404;
- непідтримуваний метод — 405 у форматі `ApiError`;
- `order=ASC` і `order=DESC` дають взаємно обернені списки; невідоме значення `sort` — 400;
- фільтр за діапазоном або пагінація повертає очікувану підмножину;
- об'єкт з українським текстом після `POST` і `GET` повертається без змін;
- паралельність: кілька запитів одночасно роблять `POST` з однією identity — рівно один 201, решта 409, у репозиторії один об'єкт (`HttpClient.sendAsync` або `ExecutorService`).
